## 2026-08-15 — GORM AutoMigrate crash-looped the API on a table backed by views

| Field | Detail |
|---|---|
| **What was wrong** | The dashboard module's `AutoMigrate` ran `db.AutoMigrate(&Metric{}...)` on `adpem.metrics` at boot. The model had `PeriodMonth time.Time` (GORM infers `timestamptz`) but the migration created the column as `date`, so AutoMigrate issued `ALTER COLUMN period_month TYPE timestamptz`. `period_month` is referenced by `v_activity_summary` and `mv_performance_monthly`, so Postgres refused: "cannot alter type of a column used by a view or rule" (SQLSTATE 0A000) → the API crash-looped, deploy unhealthy. |
| **Correct answer** | A table owned by golang-migrate AND referenced by a view/MV must NOT be AutoMigrated — GORM can't reconcile columns under a view. Make that module's `AutoMigrate` a no-op (migrations provision tables + views + MV + seed). Also pin the model column type to the migration's type (`type:date`) so model and DB never diff. |
| **Source/evidence** | Production boot log: `ALTER TABLE "adpem"."metrics" ALTER COLUMN "period_month" TYPE timestamptz` → 0A000; `fatal: auto-migrate dashboard`. |
| **Prevention rule** | Two rules: (1) If any view/MV references a table, do not run GORM AutoMigrate on it — let migrations own its whole lifecycle; the module's AutoMigrate returns nil. (2) When a migration fixes a column type, pin the GORM model's tag to the same type (`type:date`, etc.) so AutoMigrate (anywhere it still runs) never attempts an ALTER. A time.Time field silently means timestamptz — call it out when the column is really a date. |

## 2026-08-15 — Fabricated dashboard metrics from aspirational labels without checking the source API

| Field | Detail |
|---|---|
| **What was wrong** | In the dashboard ETL aggregator I emitted metrics matched to dashboard-spec LABELS, not to what the source API actually provides: `incoming_letters` = sum of two OVERLAPPING pending counts (unread ⊂ un-actioned → double-counts, corresponds to no real quantity, and isn't the "total" the label implies); `skp_count` = 1/0 presence flag mislabeled as a count; `performance_predicate_pct` = an ANNUAL SKP score coerced into a MONTHLY 0-1 %. All three looked plausible but were semantically wrong. |
| **Correct answer** | Verify every metric against the source API doc before emitting. Split the two pending surat counts into separate metrics (never sum non-disjoint counts). Drop the fake SKP count/percent; emit the real fields — SKP nilai and the talent box (`kotak_talenta`), which is the actual "predikat". Where the source has nothing (monthly performance %, total surat masuk), mark it plan, don't synthesize. |
| **Source/evidence** | Parallel workflow verification against Srikandi/Internal service/SmartASN API collections + PDFs: Srikandi dashboards expose only pending counts; Internal service totalLessonTime IS JP (doc 3.2.5); SmartASN GetDataSkp22 is annual predikat, no monthly %. |
| **Prevention rule** | Before emitting a derived/aggregate metric: (1) confirm the source actually provides the underlying value, (2) check unit + grain match (JP vs minutes, annual vs monthly, score vs ratio), (3) never sum counts that can overlap. Prefer a faithful source field over a proxy that matches an aspirational label. A metric that "looks right" but has no valid source derivation is worse than an empty column. |

## 2026-08-15 — Wrote a GORM column-rename migration using the field's json tag as the old column name, missing the real column

| Field | Detail |
|---|---|
| **What was wrong** | In migration `0003` (portal-adpem-backend, smartasn.profile_summary), I renamed the old column `pendidikan_terakhir` → `pendidikan_terakhir_nama`. But the original Go field `Pendidikan` had NO `gorm:"column:..."` tag, only `json:"pendidikan_terakhir"`. GORM derives the DB column from the FIELD NAME (`Pendidikan` → `pendidikan`), NOT the json tag. So the real column was `pendidikan`; my rename no-op'd and staging was left one column short. |
| **Correct answer** | For an untagged GORM field, the column = NamingStrategy(field name), independent of the json tag. Old column was `pendidikan`. Fixed 0003 + added defensive 0004 to rename `pendidikan` → `pendidikan_terakhir_nama`. |
| **Source/evidence** | Live `information_schema.columns` BEFORE listing showed `pendidikan` (not `pendidikan_terakhir`); post-apply verify caught the leftover `smartasn.profile_summary.pendidikan`. |
| **Prevention rule** | When writing a column-rename/repair migration, derive the OLD column names from the live DB (`information_schema.columns`) or from GORM's field-name derivation — never from the json tag (json tag ≠ column for untagged fields). And always diff the migration's planned old-names against a live BEFORE column listing in a SEPARATE step before running a destructive apply. |

## 2026-07-07 — Gated the pipeline's own operational checkpoint-table DDL behind skip_ddl, so it was never created in production

| Field | Detail |
|---|---|
| **What was wrong** | `run_3b_setup` only called `ensure_checkpoint_ddl` (creates `audit._etl_checkpoint`) when `cfg.skip_ddl=False`. `skip_ddl` defaults to `True` in production by design (mirroring pem-mpm-sync's convention, where it correctly gates GOLD BUSINESS SCHEMA DDL that a DBA owns). But `audit._etl_checkpoint` is not gold business schema — it is this pipeline's own operational bookkeeping table, created `IF NOT EXISTS` and idempotent. With the production default (`skip_ddl=True`), the table was never created, so every batch's `write_checkpoint` call would throw `UndefinedTable` on a real run. |
| **Correct answer** | `run_3b_setup` now ALWAYS calls `ensure_checkpoint_ddl`, unconditionally — `skip_ddl` no longer gates it at all. `skip_ddl` remains a DAG Param (kept for interface parity / potential future use) but currently has no effect on this pipeline, since it never issues any gold/audit business-schema DDL of its own (those tables are pre-existing, owned by the MDM/DBA team). |
| **Source/evidence** | Database reviewer: "`audit._etl_checkpoint` is never created when `skip_ddl=True` (prod default) → every batch throws `UndefinedTable` on `write_checkpoint`." |
| **Prevention rule** | Before reusing a "skip_ddl gates DDL" convention from a reference pipeline, check WHAT category of DDL it was designed to gate (there: DBA-owned business-schema tables) versus what you are ACTUALLY gating in the new pipeline (here: the pipeline's own private operational table). A flag copied for the right *name* can gate the wrong *thing* — verify the semantic category matches, not just the parameter name, especially when the new table's ownership/lifecycle differs from the reference's tables. |

## 2026-07-07 — Minted a fake uuid7() to satisfy a NOT NULL column that has no real value to reference yet

| Field | Detail |
|---|---|
| **What was wrong** | `gold.detail_individu_identities_current.last_individu_identity_validation_history_id` is `uuid NOT NULL` with no DEFAULT and no FK (a DDL gap for a Fase-1 insert, since no validation has occurred yet). ## 2026-07-07 — Satellite rows were built from every candidate PMID, not from what the master INSERT actually confirmed landed

| Field | Detail |
|---|---|
| **What was wrong** | `insert_individu_batch` used `insert_from_staging` (rowcount only) and satellites (identity/alamat/keluarga/custom_tags) were built from the full `loaded` list of candidate `LoadedIndividu` objects — the same list used to build the master-row DTOs — regardless of whether each individual row's `WHERE NOT EXISTS` guard actually let it insert. A concurrent writer (e.g. another pipeline, or a race) inserting the same NIK between this run's NIK preload and its own INSERT would cause the guard to legitimately skip that one row — but satellites for it would still be built and inserted, raising an FK violation (`penerima_manfaat_id` -> `master_individu_current`) that killed the ENTIRE batch, including the individuals that DID insert successfully. |
| **Correct answer** | Changed `insert_individu_batch` to `INSERT ... RETURNING penerima_manfaat_id` (hand-rolled SQL, since the shared `insert_from_staging` helper has no RETURNING support and was left untouched) and return `(inserted_count, inserted_pmids)`. The caller (`tasks/etl_3b_task.py`'s `_batch_worker_fn`) now filters `loaded`/`local_nik_to_pmid` down to `inserted_pmids` BEFORE building or inserting any satellite DTO, and the function was reordered so the master INSERT happens before any satellite DTO is built (previously all DTOs were built up front, before any DB write). |
| **Source/evidence** | Database reviewer: "Satellites are inserted from `loaded` regardless of whether the master row actually inserted (the WHERE NOT EXISTS guard can skip a NIK a concurrent pem-mpm-sync run already inserted) → FK violation kills the whole batch." |
| **Prevention rule** | When an INSERT uses a `WHERE NOT EXISTS` (or any conflict-skip) guard instead of a hard uniqueness violation, never assume "the rows I attempted to insert" equals "the rows that landed" — especially when downstream code (satellites, FK-dependent writes) needs to know which specific rows exist afterward. Use `RETURNING <key>` and build every downstream dependent from the returned set, not from the pre-insert candidate list — this holds even for a single-writer pipeline, since OTHER processes can still race the same target table. |

## 2026-07-07 — Per-batch checkpoint write inside worker_fn can advance past a failed batch since _worker only stopped on dead connections

| Field | Detail |
|---|---|
| **What was wrong** | Designed a sequential (n_workers=1) pipeline where `write_checkpoint` is called as the last statement inside the batch worker function, using the same connection, so batch data + checkpoint commit atomically. This correctly protects a SINGLE failed batch (rollback discards its own checkpoint write too) but missed that `tasks/_shared/orchestrator.py`'s `_worker` loop, on a per-batch exception, only set `stop_event` when `target_conn.closed` — for an ordinary (non-connection-fatal) exception it just logged the error and continued to the NEXT queued batch. Since batches are queued ahead of the single worker (bounded queue, prefetched via `queue_multiplier`), a LATER batch (higher PK) could still be pulled, processed successfully, committed, and checkpointed AFTER an earlier batch failed — permanently and silently skipping the failed batch's row range on every future resume (resume always starts strictly after `last_pk`). |
| **Correct answer** | In `_worker`'s per-batch exception handler, call `stop_event.set()` unconditionally (not only when `target_conn.closed`). Combined with the existing `if stop_event.is_set(): continue` guard at the top of each loop iteration, this makes every subsequent already-queued batch a no-op — no batch can commit or checkpoint past a failure, even with only one worker. |
| **Source/evidence** | Database reviewer flagged: "Checkpoint can advance past a failed batch → permanent silent data loss." Traced `_worker`'s control flow: the `if stop_event.is_set(): continue` check already existed (added for the coordinator/multi-worker path) but nothing set it on a plain per-batch exception — only the dead-connection branch did. |
| **Prevention rule** | When a pipeline commits a checkpoint watermark per-batch (rather than via a gap-aware coordinator), ANY batch failure — not just a fatal/connection-level one — must halt all FURTHER batches for that run, because there is no other mechanism preventing a later, independently-successful batch from checkpointing past an earlier failure. Before trusting a shared "stop on error" mechanism, verify it actually fires on the exact failure class your design depends on (here: ordinary exceptions, not just `conn.closed`) — don't assume a `stop_event` set anywhere in the code covers every path that needs it. |

## 2026-06-20 — functools.partial with positional schema arg swaps conn and schema for a 2-arg producer call

| Field | Detail |
|---|---|
| **What was wrong** | Prior fix for "multiple values for argument 'schema'" changed `functools.partial(fetch_beneficiary_rows, schema=cfg.source_schema, ...)` (keyword form → TypeError on 2-arg call) to `functools.partial(fetch_beneficiary_rows, cfg.source_schema, ...)` (positional form). Because `fetch_beneficiary_rows(conn, schema, batch_size, ...)` has `schema` in slot 1, the partial pre-fills slot 0 with `cfg.source_schema`. When `_producer` calls `fetch_fn(source_conn, batch_size)`, the expansion becomes `fetch_beneficiary_rows(cfg.source_schema, source_conn, batch_size)` — `conn=cfg.source_schema` (a string), `schema=source_conn` (a connection). Swapped. Runtime crash when the code tries to call `.cursor()` on a string. |
| **Correct answer** | Use a def wrapper, not functools.partial, when the argument to be pre-bound (`schema`) sits between the two arguments the caller supplies (`conn`, `batch_size`). The wrapper closes over `cfg` and `start_pk`, and forwards args in the correct positional order: `fetch_beneficiary_rows(conn, cfg.source_schema, batch_size, limit=cfg.limit, start_after_pk=start_pk)`. Identical pattern for `fetch_identity_rows`. |
| **Source/evidence** | User-provided verified facts: signature is `(conn, schema, batch_size, ...)`, producer calls `fetch_fn(source_conn, batch_size)` — 2 positional args. Traced the expansion: `partial(f, schema_str)(conn, batch_size)` → `f(schema_str, conn, batch_size)` → conn slot gets the string. |
| **Prevention rule** | When using `functools.partial` to pre-bind a non-first argument in a function signature, the positional partial form cannot safely express it if the caller supplies the preceding arguments positionally. Use a `def` wrapper instead. Always trace the full call expansion: `partial(f, X)(A, B)` → `f(X, A, B)` — verify each positional maps to the intended parameter. Also: regression tests for arg-binding bugs must assert the actual argument VALUES received (via a capturing mock/spy), not merely absence of TypeError — TypeError absence also passes under the swapped form if the types happen not to crash at the assertion point. |

## 2026-05-31 — format!() in tokio::join! creates a dropped temporary

**What was wrong:** Agent wrote `sqlx::query_as::<_, T>(&format!(...))` inside a `tokio::join!(...)` macro. Rust rejects this: the `String` produced by `format!()` is a temporary that is freed at the end of the `join!` statement while the query still borrows it.

**Correct answer:** Hoist the `format!()` to a `let` binding before the `tokio::join!` block so the `String` lives long enough for all futures to complete.

**Source/evidence:** `error[E0716]: temporary value dropped while borrowed` pointing at the `format!()` call inside `tokio::join!`.

**Prevention rule:** Never pass `&format!(...)` or any `&temporary_string` directly into a `tokio::join!` branch. Always `let s = format!(...);` first.

## 2026-05-01 — SQL DDL generation: inline comment swallows column separator

**Incident:** Production error `syntax error at or near "jabatan"` (PostgreSQL) when `etl_supplier_activity_task` executed `_build_create_table_ddl`. Root cause: `",\n        ".join()` pattern with inline comment `-- {json_key}` per item places the `,` separator AFTER the comment marker on the same line. SQL inline comments extend to end-of-line, so the comma is consumed — parser loses the column separator.

**Generated SQL (broken):**
```sql
email TEXT  -- email,
        jabatan TEXT  -- Jabatan,
```
The `,` after `-- email` is inside the comment — PostgreSQL never sees it.

**Files affected:**
- `airflow/dags/tasks/etl_supplier_activity_task.py` lines 52–55 (`SUPPLIER_COLUMN_MAP`)
- `airflow/dags/tasks/etl_direct_purchase_task.py` lines 52–55 (`DIRECT_PURCHASE_COLUMN_MAP`)

Pattern is structurally identical in both files — same bug, same line range.

**Why it matters:** Bug existed in the DDL builder since task creation. Only surfaced when ETL actually reached the Postgres execution step (previously failed upstream at filesystem/connection layer). Code review did not catch it because no reviewer ran the DDL string through a SQL parser.

**Fix (Option A — recommended):** Replace `-- {json_key}` with block comment `/* {json_key} */`. Block comments do not extend to end-of-line; the join-inserted `,` remains visible to the parser.

```python

f"{target} {col_type}  -- {json_key}"

# AFTER (fixed)
f"{target} {col_type}  /* {json_key} */"
```

**Prevention rule:** For SQL DDL template generation, use block comments `/* */` for inline annotations, never `-- ` line comments. When column lists are built via `join()`, verify the separator is not adjacent to a line-comment. For testing: generate a sample DDL string and validate it via `psycopg2.sql`, `sqlparse`, or a live `CREATE TABLE` against a test schema before shipping.

## 2026-05-01 — SQLAlchemy FK string resolution is per-MetaData, not per-Engine

**Incident:** `ForeignKey("public.topics.id")` in `MapsetModel` (ideas-mapedge-be) raised `NoReferencedTableError` at startup despite the FK existing correctly in the live Postgres database. The prior migration (`a7f3c9e12b84`) created the DB-level FK but registered no SQLAlchemy mapped class for `public.topics`.

**Root cause:** SQLAlchemy resolves `ForeignKey(string)` references during `configure_mappers()` against the in-memory `MetaData` of the declaring class — it does NOT query the live DB. If the target table has no mapped class sharing the same `MetaData`, resolution fails regardless of DB state.

**Key facts verified:**
- `Base.metadata is _PublicBase.metadata` → `False`. Two `DeclarativeBase` subclasses always have separate `MetaData` instances.
- `shared_models` registers `public.users` in `Base.metadata` — this is why `created_by`/`updated_by` FKs worked without an explicit stub for users.
- An isolated base (`_PublicBase`) is correct for query-only stubs that do not need to be FK-targeted by other `Base` classes. It breaks the moment another `Base`-inheriting model FK-references it via string.

**Prevention rule:** For any cross-schema FK (`ForeignKey("schema.table.col")` string form):
1. Identify which `MetaData` owns the referencing model (`Base` in most cases).
2. Confirm the target table is registered in that same `MetaData` — either via `shared_models`, an existing mapped class, or a new minimal stub inheriting the same base.
3. If adding a stub: it MUST inherit the same `DeclarativeBase` (or `Base`) as the referencing model. An isolated `DeclarativeBase` will not share MetaData.
4. Test with `configure_mappers()` before shipping — this surfaces the error before runtime.
